# External Examples — defer/async/type=module

**Rule**: [html/defer-async](https://frontendchecklist.io/rules/html/defer-async)  
**Collected**: 2026-10-06

## Example 1: Create React App (react-scripts)

Create React App uses `type="module"` for all script tags in production builds.
The `html-webpack-plugin` is configured with `scriptLoading: 'defer'` by default,
which adds the `defer` attribute to every `<script src>` in the output.

**Source**: `packages/react-scripts/config/webpack.config.js`

```js
// webpack.config.js (simplified)
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  plugins: [
    new HtmlWebpackPlugin({
      inject: true,
      scriptLoading: 'defer',
      template: paths.appHtml,
    }),
  ],
};
```

**How it works**: `scriptLoading: 'defer'` tells HtmlWebpackPlugin to add `defer`
to every injected `<script>` tag. Scripts with `type="module"` (the default output
in modern CRA) are deferred by the spec regardless.

**Key insight**: Build tools should handle this automatically. Manual `defer`
attributes are only needed when HTML is hand-written or generated by a template
engine the build does not control.

## Example 2: Next.js

Next.js adds `defer` or `type="module"` based on the script's purpose. Scripts
loaded via `<Script>` (the built-in component) support a `strategy` prop:

```tsx
import Script from 'next/script';

// Default: deferred after hydration
<Script src="/analytics.js" strategy="afterInteractive" />

// Lazy-loaded after the page is idle
<Script src="/tracking.js" strategy="lazyOnload" />

// Loaded in the <head> with defer
<Script src="/widget.js" strategy="beforeInteractive" />
```

**How it works**: Next.js decides the loading strategy per script:
- `beforeInteractive` → placed in `<head>` with no attribute (blocks for critical scripts)
- `afterInteractive` → placed after `<body>` with `defer` (default)
- `lazyOnload` → loaded after page idle via `requestIdleCallback`
- `worker` → loaded in a Web Worker

**Key insight**: For a component-based framework, the strategy is a prop, not
a hardcoded attribute. The same principle applies to any React project: wrap
the `<script>` in a component that decides based on a config, so the same rule
is enforced everywhere.

## Example 3: Vite (this project's build tool)

Vite outputs ES modules by default. All `<script>` tags in the built HTML
carry `type="module"`, which is deferred by the HTML specification:

```html
<!-- Vite build output -->
<script type="module" crossorigin src="/assets/index-Bx4kMnZk.js"></script>
<link rel="modulepreload" crossorigin href="/assets/vendor-Dfl9a1Hx.js">
```

**How it works**: Vite's `build.rollupOptions.output` produces ESM chunks. The
HTML plugin (built into Vite) injects them with `type="module"`. No explicit
`defer` is needed because module scripts are deferred by default.

**Key insight for this project**: The `frontend/index.html` already uses
`<script type="module" src="/src/main.tsx">`. This is the correct pattern for
a Vite project — `type="module"` implies `defer`, and it also enables
tree-shaking and modern JS features.

---

## Recommended patterns for this project

1. **Hand-written HTML**: Always use `type="module"` for Vite projects. Use
   `defer` for plain `<script src>` that cannot be modules.
2. **Component files** (TSX/JSX): Never hardcode `<script src>` — let the build
   tool inject scripts. If you must inject one, add `defer` or `type="module"`.
3. **Third-party scripts**: Use `async` for independent scripts (analytics,
   chat widgets) that do not depend on the DOM being ready.
4. **The guard**: `frontend/scripts/check-defer-async.mjs` enforces this at
   build time and in CI.
